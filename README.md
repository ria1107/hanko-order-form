# 印鑑販売_行政書士様向け（GAS注文フォーム）

行政書士・司法書士の先生向けに、印鑑（法人3本セット・単品・フリーメイト）を
Webフォームから注文してもらうための仕組み。GAS(Google Apps Script)がフォーム表示と
注文処理（スプレッドシート記帳・メール送信・Slack通知）を行っている。

作成者は西元さんだが、運用の都合で`sugikado@f-3.jp`アカウント内のGoogle Apps Scriptプロジェクトとして動いている。
このフォルダーは、その本番コードを**GitHubでバックアップ・履歴管理するための写し**。

| フォルダー | 用途 | 本番のGASプロジェクトID |
|---|---|---|
| `GAS_通常版(印鑑注文)/` | 通常版。送料770円・特急発送オプションあり | `1bXlGyX8gx6VI8nGUdfJZPfII0WpeIkD24iFGQrwzBS-WKg3L6QZMY_hd` |
| `GAS_中村さん専用版(送料無料)/` | 紹介者「中村さん」向け特別条件版。送料無料・納期3日固定・特急オプションなし | `1R1xSD_TgmcXqfV0QjQgcrDPvfU08TNgnMdxqQk2RW0TtobgfHgpyJigB` |

どちらも同じスプレッドシート（注文台帳）にデータを書き込む。

## セキュリティ対応（GitHub移行にあたって実施済み）

元のコードにはSlackの通知先URLや管理者メールアドレスが直接書き込まれていた。
GitHub上で誰でも見える状態は危険なため、**「スクリプトのプロパティ」**（Googleが安全に保管する設定欄。
コードとは別の場所に置かれ、GitHubには含まれない）から読み込む形に修正した。

### 設置手順（各GASプロジェクトで1回だけ）

1. 該当フォルダーのコードを Apps Script エディタに反映する（`clasp push`、または手動コピペ）
2. Apps Scriptエディタ左側の**歯車アイコン「プロジェクトの設定」**を開く
3. 一番下の「スクリプト プロパティ」で、以下の5つを追加する

| プロパティ名 | 内容 | 例 |
|---|---|---|
| `ADMIN_EMAIL` | 通知・BCC先の管理者メールアドレス | `xxxx@f-3.jp` |
| `SLACK_WEBHOOK_URL` | Slack Incoming Webhook のURL | `https://hooks.slack.com/services/...` |
| `SLACK_MEMBER_ID` | Slackでメンションする担当者のメンバーID | `U0xxxxxxx` |
| `SPREADSHEET_ID` | 注文台帳スプレッドシートのID（URLの`/d/`と`/edit`の間の文字列） | （西元さん・杉角さんが把握している実際のIDを入力） |
| `PRINTER_EMAIL` | フリーメイト発注先（印刷業者）のメールアドレス | `xxxx@xxxx.co.jp` |

※実際の値は西元さん・杉角さんが把握している値をそのまま入力すればOK。この値自体はGitHubには一切残らない。

4. 上記を設定しないまま動かすと、メール送信・Slack通知・スプレッドシート書き込みが失敗するので、
   **必ず設定してから本番の`clasp push`を行うこと**（西元さんの確認を得てから実施）。

## Notion連携(注文後の自動記録・2026-08-14追加)

`GAS_通常版_API` / `GAS_中村版_API` / `GAS_松木版_API` の3プロジェクトすべてで、
注文が入るたびに自動でNotionへ記録するようにした(`recordOrderToNotion_`関数)。

- **DB_プロジェクト**に案件ページを1件作成
  - 案件名: `{YYMMDD}_{顧客名}_印鑑注文`(例: `260814_山田太郎_印鑑注文`)
  - 開始日: 注文日 / 担当者: 杉角賢太郎 / 進捗状況: `完了(クレジット)`
  - テンプレートは既定の「サービス一覧表示_テンプレート」を適用
- **DB_現金出納帳_F3**に、注文の商品明細(Square決済に使うline_items)ごとに1行ずつ作成し、
  上記のDB_プロジェクトのページとリレーションする
  - 品目: 商品名 / 数量 / 項目: `売上` / 種別: `印鑑` / 単価(税抜): 税込価格÷1.1(四捨五入) / 課税対象: `はい(10%)`
  - 送料も明細の1行として記録される

Notionへの書き込みに失敗しても、メール送信・Slack通知・Square決済など他の処理には影響しない
(`try/catch`で囲み、エラーはログに残すのみ)。

### 設置手順(追加で必要な作業)

1. 上記3つのGASプロジェクトそれぞれの「スクリプトのプロパティ」に、`NOTION_API_KEY`という名前で
   Notionインテグレーション(Internal Integration Secret)を追加する
   (Zoomアーカイブ自動化で使っている「zoom-youtube-pipeline」インテグレーションを流用可能。
   その場合はNotion側でDB_プロジェクトとDB_現金出納帳_F3を「接続」に追加しておくこと)
2. `clasp push`で本番の3プロジェクトにコードを反映する
3. 実際にテスト注文して、Notionに正しく記録されるか確認する

## 配送先（お届け先）を別指定できる機能を追加（2026-08-27）

これまでは「送り先」セクション（お名前・メールアドレス・郵便番号・住所・電話番号）が
そのまま配送先としても使われており、印鑑の発送先を別に指定する仕組みがなかった。
スタンプ注文フォーム（`会社基盤/products/スタンプ注文_保険代理店様向け/GAS_プルデンシャル版_API/`）で
実機テスト済みの「配送先は上記と同じ」チェックボックスの仕組みをそのまま応用し、
**通常版・松木版・中村版すべて**に配送先セクションを追加した。

### 通常版・松木版（`docs/`・`docs-matsuki/` ＋ `GAS_通常版_API`・`GAS_松木版_API`）

- 「送り先」セクションの下に「配送先」セクションを新設
- チェックボックス「配送先は上記と同じ」（**デフォルトON**）
  - ONのまま送信 → 送り先の郵便番号・住所・お名前をそのまま配送先として使う
  - チェックを外す → 配送先専用の郵便番号（住所検索ボタン付き）・住所・お届け先氏名が表示され、その内容を配送先として使う（この時だけ必須）

### 中村版のみ特殊仕様（`docs-nakamura/` ＋ `GAS_中村版_API`）

中村様は毎回ほぼ同じ事務所宛てに送るため、他の版とは**逆の初期状態**にしてある。

- チェックボックスのラベルは「**中村様事務所以外に送る**」、**デフォルトOFF**
- OFFのまま送信 → コード内に固定で書いてある中村様事務所の住所を配送先として使う（`GAS_中村版_API/Code.js`の
  `NAKAMURA_OFFICE_ZIP` / `NAKAMURA_OFFICE_ADDRESS` / `NAKAMURA_OFFICE_NAME` / `NAKAMURA_OFFICE_TEL`）。
  住所や電話番号が変わった場合はこの4つの定数だけ書き換えればよい
- ONにする → 配送先専用の郵便番号・住所・お届け先氏名の入力欄が表示され、入力内容を配送先として使う（通常版と同じ動き）

**2026-08-29追記**: 配送先専用の入力欄に「配送先電話番号」も追加した（通常版・松木版はチェックを外した時、
中村版は「中村様事務所以外に送る」にチェックを入れた時に必須表示。中村版でチェックを外した場合は
`NAKAMURA_OFFICE_TEL`を使用）。

### 決定した配送先の反映先

いずれの版も、決定した配送先（郵便番号・住所・お届け先氏名・電話番号）を以下すべてに反映している。

- お客様への確認メール本文の「【お届け先】」欄
- 担当者へのSlack通知の「■お届け先」欄
- 注文台帳スプレッドシートへの記帳（次項）

なお「フリーメイト印刷業者への発注ドラフトメール」（`createPrinterDraftOnlyFreimate`関数）は、
もともと配送先の住所を扱っていない（校正確認のためのメールで、発送先の記載がない仕様）ため、
今回は変更していない。発送先を含める必要が出てきた場合は追加対応が必要。

### スプレッドシート側で必要な対応（重要・手動作業）

**集計が崩れるため、既存の列の並び順・挿入は絶対に行わないこと。**
注文台帳（`注文台帳_総合`シート）の一番右（末尾）に、新しい列を4つ追加する必要がある。

```
...（既存の最後の列）備考 | 配送先郵便番号（新規） | 配送先住所（新規） | お届け先氏名（新規） | 配送先電話番号（新規）
```

- 通常版・松木版・中村版のすべてで、この4列を同じ並び（郵便番号→住所→氏名→電話番号）で末尾に追加する
- 列を追加する前に本番反映すると、`appendRow`で書き込んだ配送先データが列不足のままシートの右端に
  追記される（ヘッダーとズレる）ので、**必ず列を追加してから`clasp push`すること**

### 3. 材質・商品ごとの納期（発送までの営業日数）ルールを追加

これまでは「特急オプションの有無」等バージョンごとに1つの固定ロジックだったが、
**注文に含まれる商品・材質によって納期が変わる**ように変更した（3バージョン共通のルール）。

- フリーメイトを含む注文 → **7営業日以内に発送**
- ブラストチタンを含む注文（法人3本セットの材質 or 単品のいずれか） → **10営業日以内に発送**
- 黒水牛を含む注文 → **2営業日以内に発送**（**松木版のみ適用**。通常版・中村版は変更なし）
- 薩摩本柘は変更なし（各版の基本納期がそのまま適用される）

1回の注文に複数の商品・材質が混ざる場合は、**最も日数のかかるものに合わせる**
（各版の基本納期・フリーメイト・ブラストチタン・（松木版のみ）黒水牛の日数のうち最大値を採用）。
基本納期のまま変わらない場合は今まで通りの表示文言、上書きされた場合は
「◯営業日以内に発送（ブラストチタンを含むため）」のように理由付きの文言になる。

- **Code.js側**: `_singleHasMaterial(formData, keyword)`で単品チェックボックスの中に
  `checkboxField`名に'Titan'/'Kuro'を含むチェック済み項目があるかを判定し、
  `_resolveDeliveryType(baseDays, baseLabel, hasFrei, hasTitan, hasKuro)`で最終的な
  `deliveryType`（文言）を決定する。既存の`deliveryType`を使う箇所（確認メール・Slack通知・
  `createPrinterDraftOnlyFreimate`への引数）は変更していない。
- **フロント（index.html）側**: 同じ考え方の`singleHasMaterial(keyword)`・
  `resolveDeliveryLabel(...)`をJSに追加し、`updatePrice()`内で`id="deliveryLabel"`の
  表示テキストをリアルタイム更新するようにした（中村版・松木版はこれまで納期表示が
  固定文言だったため、今回新設）。
